# نظام أوامر التعميد + نظام الاعتماد الإلكتروني

نظام ويب حقيقي متعدد المستخدمين (خادم Node.js + قاعدة بيانات PostgreSQL) يدير دورة حياة
أمر التعميد كاملة: إنشاء ← إرسال للاعتماد ← اعتماد/رفض/إعادة للتعديل ← تصدير PDF مع اعتماد
إلكتروني وQR Code للتحقق.

---
 
## 1. ما الذي بُني فعليًا

- **حسابات ومصادقة حقيقية**: تسجيل دخول بكلمة مرور مشفّرة (bcrypt) وجلسات محفوظة في قاعدة البيانات.
- **صلاحيات (Roles)**: موظف / معتمد / مدير النظام — كما طلبت بالضبط.
- **حالات أمر التعميد**: مسودة، بانتظار الاعتماد، معتمد، مرفوض، معاد للتعديل.
- **زر "إرسال للاعتماد"**: يقفل التعديل على الموظف حتى تتم المراجعة أو تُعاد له.
- **صفحة "طلبات الاعتماد"**: تُظهر للمعتمد فقط الطلبات التي تنتظره فعليًا (حسب الدور والمستوى).
- **أزرار اعتماد / رفض / إعادة للتعديل** مع تسجيل: اسم المستخدم، التاريخ، الوقت، وسبب/ملاحظة عند الرفض أو الإعادة.
- **منع التعديل بعد الاعتماد** فعليًا على مستوى الخادم (Route)، وليس مجرد إخفاء زر في الواجهة.
- **سجل عمليات (Audit Log) إضافة فقط**: لا يوجد في كامل النظام أي مسار (route) يعدّل أو يحذف من هذا الجدول — لا للموظف ولا للمعتمد ولا حتى لمدير النظام من الواجهة.
- **مستويات اعتماد متعددة قابلة للتوسعة**: جدول `approval_levels_config` يحدد ترتيب المستويات، ويمكن لمدير النظام إضافة مستويات جديدة (مسؤول تعميد ← مدير مشروع ← مدير مالي ← مدير عام...) من صفحة الإعدادات دون أي تعديل برمجي.
- **تصدير PDF عبر المتصفح** (نفس أسلوب النظام الأصلي: طباعة/حفظ كـ PDF)، مع ظهور:
  - "بانتظار الاعتماد الإلكتروني" إن لم يُعتمد بعد.
  - "معتمد إلكترونيًا" + اسم المعتمد + المسمى الوظيفي + التاريخ والوقت، إن اعتُمد.
- **QR Code** يظهر تلقائيًا في نسخة PDF بعد الاعتماد، ويفتح صفحة تحقق عامة (`/verify/...`) لا تتطلب تسجيل دخول، تعرض فقط: رقم الأمر، المشروع، المقاول، القيمة، الحالة، اسم المعتمد وتاريخه — بدون أي بيانات حساسة أخرى. الرابط يستخدم رمزًا عشوائيًا (token) غير قابل للتخمين، وليس رقم الأمر نفسه.

## 2. ما تم تبسيطه عمدًا في هذه النسخة الأولى (MVP)

- إدخال بنود الأعمال حاليًا حقول نصية عادية (مثل النظام الأصلي قبل خاصية البحث الذكي). يمكن لاحقًا نقل مكتبة البنود الـ 208 والبحث الذكي التي بنيناها في النسخة السابقة إلى هذا النظام كخطوة تالية.
- المرفقات (Attachments) غير مُفعّلة بعد — البنية جاهزة لإضافتها (يحتاج تخزين ملفات، مثل خدمة تخزين سحابية).
- عند "إعادة للتعديل" ثم إعادة الإرسال، تُعاد جميع مستويات الاعتماد للبداية (تبسيط مقصود لأول نسخة؛ يمكن تعديله لاحقًا ليستكمل من نفس المستوى إذا احتجت ذلك).

## 3. التشغيل محليًا (لتجربة النظام على جهازك قبل النشر)

يتطلب: [Node.js](https://nodejs.org) نسخة 18 فأعلى، و PostgreSQL (يمكن تنزيله محليًا، أو استخدام حساب مجاني من [Neon](https://neon.tech) أو [Railway](https://railway.app) للتجربة السريعة بدون تثبيت شيء).

```bash
cd tawmeed-approval
npm install
cp .env.example .env
# افتح .env وضع رابط قاعدة بياناتك الحقيقي في DATABASE_URL

npm run seed     # ينشئ الجداول + 3 حسابات تجريبية (يطبعها في الطرفية)
npm start        # يشغّل الخادم على http://localhost:3000
```

## 4. النشر السحابي المجاني/الرخيص عبر Railway (الأسهل لمن لا يملك خبرة برمجية)

هذه خطوات عملية كاملة من الصفر:

### الخطوة 1 — ارفع المشروع على GitHub
1. أنشئ حسابًا على [github.com](https://github.com) إن لم يكن لديك.
2. أنشئ مستودعًا (Repository) جديدًا فارغًا، مثلًا باسم `tawmeed-approval`.
3. ارفع كل ملفات هذا المشروع إليه (يمكنك سحب المجلد مباشرة عبر واجهة GitHub الويب "Upload files"، أو باستخدام Git إن كنت تعرفه).

### الخطوة 2 — أنشئ حساب Railway واربطه بـ GitHub
1. افتح [railway.app](https://railway.app) وسجّل دخول باستخدام حساب GitHub نفسه.
2. اضغط **New Project** ← **Deploy from GitHub repo** ← اختر المستودع `tawmeed-approval`.
3. سينشئ Railway تلقائيًا خدمة (Service) لتطبيقك ويبدأ محاولة تشغيله.

### الخطوة 3 — أضف قاعدة بيانات PostgreSQL
1. داخل نفس المشروع في Railway، اضغط **New** ← **Database** ← **Add PostgreSQL**.
2. Railway سيُنشئ القاعدة تلقائيًا **ويضيف متغيّر `DATABASE_URL` لتطبيقك تلقائيًا** — لا تحتاج نسخه يدويًا.

### الخطوة 4 — أضف المتغيّرات المتبقية
داخل خدمة التطبيق (وليس قاعدة البيانات) اذهب لتبويب **Variables** وأضف:
- `SESSION_SECRET` = أي نص عشوائي طويل (مثلًا 40 حرفًا عشوائيًا).
- `BASE_URL` = رابط تطبيقك بعد النشر (Railway يعطيك رابطًا تلقائيًا شكله `https://xxxx.up.railway.app` — انسخه هنا بعد أول نشر ناجح، ثم أعد النشر). هذا الرابط يُستخدم لبناء رابط QR Code فقط.
- `NODE_ENV` = `production`

### الخطوة 5 — أنشئ الجداول والحسابات التجريبية
1. من لوحة Railway، افتح تبويب الخدمة ← **Settings** ← فعّل **One-off command** أو استخدم زر **"Run command"** إن توفر.
2. شغّل الأمر: `npm run seed`
   - إن لم تجد خيار تشغيل أمر مباشر في واجهة Railway، يمكنك تثبيت [Railway CLI](https://docs.railway.app/guides/cli) على جهازك وتشغيل: `railway run npm run seed`

### الخطوة 6 — افتح الرابط
افتح رابط التطبيق (`https://xxxx.up.railway.app`) وسجّل الدخول بأحد الحسابات التجريبية التالية (تُطبع أيضًا في سجل التشغيل بعد `npm run seed`):

| الدور | البريد الإلكتروني | كلمة المرور |
|---|---|---|
| موظف | employee@example.com | Employee@123 |
| معتمد | approver@example.com | Approver@123 |
| مدير النظام | admin@example.com | Admin@123 |

**غيّر كلمات المرور هذه فورًا من أول استخدام حقيقي**، وأنشئ حسابات موظفيك الفعليين من صفحة "المستخدمون" (تظهر فقط لمدير النظام).

## 5. أمان يجب مراعاته قبل الاستخدام الفعلي في العمل

- غيّر `SESSION_SECRET` لقيمة عشوائية طويلة وسرّية فعلًا.
- غيّر كلمات مرور الحسابات التجريبية الثلاثة فورًا (أو احذفها من صفحة المستخدمين بعد إنشاء حسابات حقيقية).
- تأكد أن الرابط يعمل عبر HTTPS دائمًا (Railway يوفر ذلك تلقائيًا لكل تطبيق منشور عنده).
- راجع صلاحيات قاعدة البيانات على مستوى Postgres نفسه إن أردت طبقة حماية إضافية لسجل العمليات (audit_log) بحيث لا يستطيع حتى من يملك وصولًا مباشرًا لقاعدة البيانات التعديل عليه بسهولة (مثل صلاحيات REVOKE UPDATE, DELETE).

## 6. هيكل المشروع
.
```
tawmeed-approval/
  server.js              نقطة تشغيل الخادم
  db.js                  الاتصال بقاعدة البيانات
  audit.js               دالة تسجيل سجل العمليات (المسار الوحيد للكتابة فيه)
  schema.sql              مخطط قاعدة البيانات الكامل
  seed.js                 إنشاء الجداول + حسابات تجريبية
  middleware/auth.js      التحقق من تسجيل الدخول والصلاحيات
  routes/
    auth.js                تسجيل الدخول / الخروج
    orders.js               إنشاء/تعديل/عرض/طباعة أوامر التعميد + إرسال للاعتماد
    approvals.js             طلبات الاعتماد + اعتماد/رفض/إعادة للتعديل
    admin.js                 المستخدمون + كل الأوامر + سجل العمليات + إعدادات مستويات الاعتماد
    verify.js                صفحة التحقق العامة عبر QR
  views/                  كل صفحات الواجهة (EJS)
  public/css/style.css    التنسيق العام
```

## 7. خطوات مقترحة للتطوير لاحقًا

- نقل مكتبة بنود الأعمال (208 بندًا) والبحث الذكي من النظام السابق إلى نموذج إنشاء الأمر.
- دعم رفع المرفقات (صور/ملفات PDF) وربطها بالأمر.
- ربط كل مستوى اعتماد بمستخدم/مستخدمين محددين بدلاً من الدور العام فقط.
- إشعارات بريد إلكتروني عند الإرسال للاعتماد أو الاعتماد أو الرفض.
